Loci — app map

A snapshot of the code at commit a203896 (2026-10-05, refreshed at shipping; first drawn at e7b39bc). The code can move on after this; the paths and names below were checked against that commit.

Loci turns one photo of your own room into a memory palace for a list. It puts each item on a real object along one route, writes a short scene for each stop, and then tests you with the lights out: every item you remember turns its stop green and lights that part of the room again.

The main pieces

  • The app in the browser — src/. Screens (src/screens/Home.tsx, src/screens/Palace.tsx), the photo stage with pins and route (src/components/Stage.tsx), and the learn, recall and result panels.
  • Two small server helpers — api/anchors.ts finds objects in the photo (Gemini, DeepSeek last); api/scenes.ts writes one scene per stop from object names only. They hold the AI keys, which never reach the browser.
  • Plain rules the AI never overrides — shared/route.ts (which objects become stops, and the route), shared/score.ts (is an answer right?), shared/voice.ts (what a spoken phrase means).
  • Storage on the device — src/lib/store.ts keeps palaces, photos and results in the browser's IndexedDB.
  • Speech-to-text — src/lib/speech.ts wraps the browser's own Web Speech API for spoken recall.

One action, followed through the code

You type an answer during recall and press Enter. Here is where it goes, and how it ends up as a green pin with a pool of light.

The route, stop by stop

  1. src/components/RecallPanel.tsx — the answer form's onSubmit ignores an empty box, then calls onAnswer(text) and clears the box for the next stop. The input has autocorrect, autocapitalise and spellcheck off, so the phone keyboard can't change your answer.
  2. src/screens/Palace.tsx — onAnswer runs const ok = isRight(text, askingStop.item), then respond(ok, …). respond() moves the walk on with answer(w, right, Date.now()) from src/lib/recall.ts and hands it to commit(), which shows the feedback line and, after the last stop, calls finish(). finish() works out the result, stores the walk on the device, and only then shows the result, so leaving right away never loses the score. Spoken answers arrive through onPhrase.current and reach the same commit().
  3. shared/score.ts — normalize() lowercases, strips accents, punctuation and a leading "1."; closeEnough() compares word by word: distance() (typing changes, a swap of neighbours counts once) must stay within allowance(word length) — 0 for up to 4 letters, 1 for 5–9, 2 for 10 or more — and within MAX_TOTAL_TYPOS (3) overall; words run together ("oatmilk") also match. isRight() tries the item and every accepted answer.

Back on screen, Palace.tsx turns the walk into pinStates and lit; src/components/Stage.tsx draws .pin[data-state="right"] with a tick and opens that stop's circle.pool in the mask over the dark room.

A practice to reuse

Before trusting a "close enough" rule, write down the pairs that must match and the pairs that must not, and make them tests.

What happened here: the first plan used one typo allowance for the whole answer. The spec listed "Vitamin C" vs "Vitamin D" and "Henry VII" vs "Henry VIII" as answers that must be wrong. Worked through, a whole-answer allowance of 1 would have accepted both. So the rule became per word, with short words exact. The evidence is in tests/score.test.ts: "needs short words exactly" and "forgives up to the allowance and not one more". A later test, "never accepts a different item from the same list", checks all 132 pairs of cranial nerves.

Where else it helps: search boxes, duplicate detection, "did you mean", matching names across lists. Any time an agent writes a tolerant comparison, ask it for the must-match and must-not-match table first, and keep the table as tests.
